# Generated Aldor code performance benchmark

This benchmark was introduced for v0.12 and is intended to remain a release
sealing gate.

The workload is the existing Algebra `sm_dmp0` test for
`DistributedMultivariatePolynomial0`, with one deliberate change: the shared
`RandomNumberGenerator` is seeded with 1 before the four 1000-polynomial zoos
are created.  This preserves the existing workload while making it exactly
reproducible.

The primary question is the execution speed of code generated by Aldor.  For
compiler-version bisection within one generated-code ABI, the support root
(runtime, `libaldor`, and `libalgebra`) is held fixed.  Only the compiler used
for the benchmark translation unit changes.

v0.16 deliberately fixes the historical export-type hash, which changes the
generated dispatch identity and therefore creates an ABI boundary: a v0.01
translation unit cannot safely execute against v0.16-generated Algebra
libraries.  Across such an ABI boundary the harness supports separate generated
support roots with `BENCH_BASELINE_SUPPORT_ROOT` and
`BENCH_CURRENT_SUPPORT_ROOT`.  The two roots must be built from the same Aldor
library sources and host runtime/toolchain; only the generated export-hash ABI
is allowed to differ.  v0.16's baseline support libraries are rebuilt with a
modern bridge compiler retaining the historical hash, so obsolete v0.01 C
generation is not reintroduced merely to construct the libraries.

The Aldor optimization options are `-O -Qall`.  Aldor does not parse `-O3` as a
single option, so the harness inserts a `gcc` wrapper which appends `-O3` to the
backend command.  Since the last GCC optimization-level option wins, generated
C is compiled at effective `-O3`.

The harness also records paired compiler+generated-C compilation time,
alternating baseline/current order.  Compilation timing is a secondary metric:
the primary release question remains execution speed of the generated program.

The executable output must be byte-identical before execution timing.  The
harness pins both variants to the same CPU, performs warmups, alternates
baseline/current run order, and records both wall time and process CPU time.
Process CPU time is the primary metric on shared hosts.

Run with:

    run-generated-code-benchmark.sh \
        SUPPORT_ROOT BASELINE_COMPILER CURRENT_COMPILER [OUTDIR]

The default is 5 paired compilation measurements, 2 execution warmups and 7
paired measured execution runs.  `BENCH_COMPILE_RUNS`, `BENCH_RUNS` and
`BENCH_WARMUPS` may be increased for a release seal.

## v0.18rc2 timing configuration

The v0.01 comparison is again part of RC acceptance.  Because the corrected
export-hash / `.ao` ABI is not readable by the original v0.01 compiler, do not
let the baseline side silently inherit the current support root.

`distro/build.sh all` accepts either the traditional pair:

    ALDOR_BENCH_BASELINE_COMPILER
    ALDOR_BENCH_BASELINE_SUPPORT_ROOT

or the shorthand aliases:

    ALDOR_V001_COMPILER
    ALDOR_V001_SUPPORT_ROOT

The baseline support root must use the historical hash/ABI built from the same
high-level library source snapshot, following the provenance recorded for the
v0.16/v0.17 benchmark runs.  The current support root defaults to the newly
built candidate root.

The original v0.01 compiler also predates the 8-byte external `ALDOAO`
envelope now placed around each `.ao` payload.  A historical-hash bridge made
with the current compiler therefore needs one container-only compatibility
step before it is supplied to v0.01: strip exactly those 8 envelope bytes from
each `.ao` member/loose `.ao`.  The internal library payload remains unchanged.
This is the procedure used for the recorded v0.18rc2 timing run; see
`results/v0.18-rc2-provenance.txt`.
